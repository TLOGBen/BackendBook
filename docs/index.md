# 後端基本功：59 個新人一定會遇到的主題

> 給新進後端工程師的入門教材。每篇講一個主題：它要解決什麼問題、核心的想法是什麼、在什麼情況下會出事、怎麼避開，以及哪些是一定要會的基本功、哪些先知道就好。

共 59 篇，全部讀完約 21 小時。不用一次讀完，照下面的路線一週讀幾篇就好。

第一次來，先看[系列全貌圖](overview.md)：用 9 張圖從一個最簡單的請求開始，一層一層加上快取、擴展、非同步和維運，最後打開 API 伺服器看程式裡面怎麼分層，每一層都標出對應的文章。

## 每篇都長這樣

| 段落 | 用途 |
|---|---|
| 開頭定義 | 一句只用基本詞彙寫成的定義 |
| 核心問題與理念 | 它要解決什麼問題、核心的想法（一句白話），以及「想通的那一步」：直覺的做法卡在哪裡、哪一個轉念讓問題迎刃而解 |
| 閱讀前推薦具備知識 | 讀這篇需要先會什麼、要會到什麼程度、不熟的話先看哪裡，附一題自我檢查 |
| 為什麼要在意 | 一個具體的假設情境：出事的程式碼、兩個請求在 T1、T2 各做了什麼、使用者和工程師各看到什麼 |
| 全貌：它在系統裡的位置 | 一張小圖，標出這個主題發生在系統的哪裡 |
| 生活比喻 | 先有直覺，再看細節 |
| 它是怎麼運作的 | 先講這個機制解決什麼問題，再一步步講它怎麼運作，圖一張張加元件 |
| 動手看看 | 能在本機跑的範例，多半用 Docker 起 PostgreSQL 或 Redis，都實際跑過 |
| 常見地雷 | 新人常犯的錯，錯誤寫法和正確寫法並排 |
| 重點整理 | 讀完全文後對照用，裡面每個詞前文都解釋過 |
| 新人必知清單 | 分成「一定要會」「知道有這回事就好」「先不用管」三層，告訴你現在該花力氣在哪裡 |
| Code Review 時可以問的問題 | 看 PR 時拿來檢查 |
| 情境演練 | 工作上會遇到的狀況，先想自己會怎麼做，再點開看答案和理由 |

範例統一使用 **PostgreSQL**、**Redis** 和 **Python**；MySQL 行為不同的地方，文中會另外註明。第十二章「設計與分層」的範例和練習題改用 **Java 21** 和 **JUnit 5**。

## 時間不多的話，先讀這 15 篇

這幾篇的內容，新人在第一個月的 code review 裡幾乎一定會碰到：

1. [資料庫交易](03-資料庫交易.md)：把多個資料庫操作綁成一包，要嘛全部生效，要嘛全部當沒發生
2. [競爭條件](01-競爭條件.md)：多個請求同時讀改寫同一筆資料，結果看誰先跑到哪行而出錯
3. [資料庫索引](10-資料庫索引.md)：索引是排好序的目錄，讓查詢不用翻整張表，代價是寫入變慢
4. [N+1 查詢](09-N+1%20查詢.md)：迴圈裡每筆再各查一次資料庫，1 次能做完的事變成 1+N 次來回
5. [連線池](08-連線池.md)：先開好一批資料庫連線重複借用，用完馬上還，不要每次都重新連
6. [唯一約束](14-唯一約束.md)：讓資料庫保證某個值在整張表只出現一次，並行寫入也擋得住
7. [資料庫遷移](15-資料庫遷移.md)：把 schema 變更寫成有編號的程式碼，進版控、經 review、依序自動套用
8. [冪等性](25-冪等性.md)：同一操作做一次或做十次結果都一樣，重試才安全
9. [重試機制](26-重試機制.md)：只重試暫時性錯誤，前提是操作冪等，要有次數和時間上限，而且只在一層重試
10. [快取失效](21-快取失效.md)：資料庫改了之後，讓快取裡的舊副本及時作廢，別再被拿出來用
11. [同步與非同步](51-同步與非同步.md)：等結果時要停住，還是先做別的？分清程式呼叫和服務之間兩層
12. [背景工作者](37-背景工作者.md)：把耗時工作移出請求丟進佇列，交給獨立 worker 慢慢做
13. [健康檢查](49-健康檢查.md)：平台定期問服務活著沒、能接客沒，再決定重啟或暫停送流量
14. [傳統測試方式](52-傳統測試方式.md)：單元、整合、端對端等測試各抓哪種錯，以及為什麼不能都靠 mock
15. [依責任分層](58-依責任分層.md)：看「誰會來改它」決定程式放哪一層，同一種改動只改一處

## 怎麼用這份教材

- **自學**：照學習路線每天讀一到兩篇。讀完先試「情境演練」，想不出怎麼處理就回頭重看對應的段落。
- **帶新人**：每週挑一個階段。讀完後拿「為什麼要在意」的情境和新人討論：如果是你，會從哪個症狀發現、怎麼修。
- **Code review**：看到相關的程式碼時，把對應篇章的連結貼給對方，並拿「Code Review 時可以問的問題」當檢查清單。
- **動手做**：「動手看看」的範例大多只要 Docker 就能跑。自己跑一次，親眼看到兩個交易互相卡住、庫存被扣成負數，會比只讀文字記得牢。

## 撰寫與查核說明

每篇寫完後經過四輪處理：

1. **書面查核**：審稿代理對照官方文件，逐條確認版本號、預設值、錯誤碼和設定名稱，並檢查程式碼、圖表、用語和連結。
2. **實跑驗證**：在 Docker 上用文章指定的版本（PostgreSQL 16／17、Redis 7.x、RabbitMQ 4、Nginx、Jaeger）實際執行「動手看看」和其他範例，輸出跟文章不符的地方改成實際結果。
3. **文字調整**：依 `/baransu:write` 的寫作規則和 `/baransu:teach-me` 的教學方式調整文字：先講每個機制解決什麼問題再講怎麼運作，同一個概念全篇用同一個名字，拿掉翻案句和套話。
4. **新人視角審閱**：審閱代理用剛入行工程師的眼光逐段打「理解難度」分數，把術語先用後講、跳步、太密的地方補平；用到術語的重點整理移到文末，開頭只放白話的核心問題與理念，情境改寫成看得到程式碼和時間軸的具體案例，並為每篇加一張全貌圖和一張可以播放的主圖。每篇改前改後的難度曲線見[難度地圖](difficulty.md)。

沒辦法在本機跑的部分（Kubernetes、AWS、Kafka 叢集、MySQL、PostgreSQL 18 以後的新功能）只做了書面查核。範例輸出裡的執行時間、tps 這類數字依機器而異，是示意。發現錯誤請直接修改該篇。
